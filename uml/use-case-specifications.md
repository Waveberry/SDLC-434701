# Спецификация актёров и прецедентов (Use Case Specifications) проекта Cheq

Документ сопровождает диаграмму вариантов использования ([01-use-case.png](diagrams/01-use-case.png), исходник [01-use-case.puml](models/01-use-case.puml)) и содержит краткие описания всех актёров (1–2 строки) и полные потоки событий (Flow of Events) для каждого из 10 прецедентов (`UC-01`–`UC-10`) в соответствии с методическими требованиями ЛР № 5.

---

## 1. Описания актёров (Actors)

| Актёр | Тип | Краткое описание роли в системе (1–2 строки) |
|---|---|---|
| **Владелец архива (Пользователь)** | Первичный (человек) | Физическое лицо, ведущее личный учёт чеков, товаров, карт и месячного бюджета на Android-устройстве. Инициирует сценарии ввода, проверки, поиска, аналитики, управления картами, шаблонами и бэкапами. |
| **Системные службы Android** | Вторичный (внешняя система) | Платформенные сервисы ОС (CameraX, Photo Picker, `ConnectivityManager`, `FileProvider`, Storage Access Framework), обеспечивающие захват и выбор фото, контроль сети и безопасный обмен файлами. |
| **Groq API** | Вторичный (внешняя система) | Облачный HTTPS-сервис (`openai/gpt-oss-20b`, strict JSON Schema), выполняющий структурированный разбор очищенного OCR-текста чека в черновик покупки. |
| **API НБРБ** | Вторичный (внешняя система) | Публичный HTTPS-сервис Национального банка Республики Беларусь (`api.nbrb.by/exrates`), поставляющий официальные исторические курсы валют на дату покупки без авторизации. |
| **Планировщик времени ОС (Время)** | Вторичный (время) | Системные часы и планировщик таймеров, инициирующие отложенные повторы очереди распознавания по истечении backoff (`UC-09`) и очистку временных TXT-экспортов старше 24 часов (`UC-05`). |

> **Примечание по правилам UML:** связи между актёрами на диаграмме прецедентов не моделируются, так как действующие лица находятся вне границ системы Cheq и не образуют иерархии обобщения поведения.

## 2. Спецификации прецедентов (Flow of Events)

### UC-01: Импортировать и проверить чек с фото

- **Краткое описание:** Позволяет пользователю сфотографировать бумажный чек или выбрать изображение из галереи, выполнить локальный гибридный OCR и облачный разбор Groq, проверить арифметику и явно сохранить покупку в архив.
- **Актёры и связи:** Владелец архива (инициатор), Системные службы Android, Groq API; включает `<<include>>` **UC-08 (Проверить арифметику и валидность чека)**; расширяется через `<<extend>>` прецедентом **UC-09 (Обработать офлайн-очередь и повторы)**.
- **Предусловия:** Приложение Cheq установлено; на устройстве достаточно свободной памяти для сохранения локальной JPEG-копии чека (`files/receipts/`).
- **Основной поток событий:**
  1. Прецедент начинается, когда пользователь нажимает кнопку добавления чека (`+`) и выбирает «Снять камерой» (`CameraActivity`) или «Выбрать фото» (Photo Picker).
  2. Системные службы Android возвращают URI изображения; `EditorActivity` передаёт его в `RecognitionQueue.addPhoto(uri, defaultCurrency)`.
  3. Система сохраняет запись со статусом `waiting` (`revision = 0`) в `pending_receipts.db`, копирует фото в приватное хранилище (JPEG 90%) и немедленно возвращает управление интерфейсу.
  4. Фоновый поток `RecognitionQueue.worker` переводит запись в `processing`, корректирует EXIF-ориентацию, разрезает длинный чек на перекрывающиеся полосы (`OcrPreparation.bands()`, ≤ 24 полосы) и запускает гибридный локальный OCR (ML Kit Latin + Tesseract `rus+eng`).
  5. `OcrTextMerger.merge()` объединяет результаты с приоритетом кириллицы и сохраняет `raw_text` в `pending_receipts.db` (CAS-проверка по `revision`).
  6. При наличии подтверждённой сети (`NET_CAPABILITY_VALIDATED`) `GroqClient` отправляет HTTPS POST (только OCR-текст, валюта и дата по умолчанию) в Groq API с таймаутом `55 с`.
  7. Groq API возвращает JSON по схеме `purchase_receipt`; система выполняет детерминированную постобработку `ReceiptExtraction.reconcile()` и проверку последних 4 цифр карты `verifyCardLastFour()`.
  8. Система проверяет совпадение `revision` (CAS) и переводит запись в статус `ready`, уведомляя редактор через `LiveData`.
  9. Пользователь просматривает распознанные поля и позиции; выполняется включённый прецедент **UC-08** (`ReceiptArithmetic.discrepancies()`).
  10. Пользователь при необходимости корректирует поля, привязывает карту и нажимает «Сохранить покупку».
  11. `ReceiptStore.savePending()` в единой ACID-транзакции записывает покупку, позиции (`items`) и маркер `completed_pending`, затем удаляет запись из очереди.
  12. Прецедент завершается; новая покупка отображается в архиве.
- **Альтернативные потоки:**
  - **A1 (Нет сети или отсутствует `GroqApi.key`):** на шаге 6 срабатывает точка расширения **UC-09** — запись остаётся в `waiting` с сохранённым OCR-текстом и фото для последующего автовозобновления либо ручного заполнения.
  - **A2 (Пользователь изменил черновик до прихода ответа Groq):** на шаге 8 метод `edit()` уже увеличил `revision`; CAS-проверка не совпадает, поздний ответ Groq не перезаписывает правки пользователя, а `resetStale()` переводит элемент на повторный разбор.
  - **A3 (Отказ одного из OCR-движков):** на шаге 4 при сбое ML Kit или Tesseract система использует результат работоспособного движка; при низком качестве Tesseract выполняет контрастный проход (`PSM_SPARSE_TEXT`).
- **Потоки ошибок:**
  - **E1 (Ошибка Groq: HTTP 401/403/429, таймаут 55 с, невалидный JSON):** `GroqErrors` классифицирует причину, запись переходит в `error`, `failures` увеличивается (≤ 6), планируется экспоненциальный backoff `min(60 с, 2 с << (failures − 1))` (**UC-09**); фото и текст сохраняются.
  - **E2 (Повторное нажатие «Сохранить» или сбой очистки очереди):** таблица `completed_pending` возвращает существующий `receipt_id`, предотвращая дублирование покупки.
- **Постусловия:** Покупка атомарно сохранена в `receiptbox.db`, запись удалена из `pending_receipts.db`, фото связано с сохранённой покупкой.

### UC-02: Добавить или редактировать покупку вручную (включая шаблоны F-16)

- **Краткое описание:** Позволяет пользователю создать новую покупку вручную (в том числе чек без позиций, покупку по шаблону `F-16` или быстрый повтор существующего чека), отредактировать сохранённый чек или сохранить его как шаблон.
- **Актёры и связи:** Владелец архива (инициатор); включает `<<include>>` **UC-08 (Проверить арифметику и валидность чека)**.
- **Предусловия:** Приложение запущено; при редактировании, дублировании или создании из шаблона исходный чек/шаблон существует в `receiptbox.db`.
- **Основной поток событий:**
  1. Прецедент начинается, когда пользователь выбирает «Ввести вручную», «Из шаблона» (в меню `+`), «Повторить покупку» (в карточке чека) либо открывает чек для правки.
  2. `EditorActivity` и `EditorModel` открывают форму; при выборе шаблона (`draftFromTemplate`) или дублирования (`duplicateDraft`) подставляется текущая дата (`LocalDate.now()`), копируются магазин, валюта, карта и позиции.
  3. Пользователь заполняет или изменяет магазин, дату, валюту, итоговую сумму, банковскую карту и список позиций.
  4. Выполняется включённый прецедент **UC-08**: проверяются доменные ограничения (`ReceiptDraft.validate()`) и расхождения (`ReceiptArithmetic.discrepancies()`).
  5. Пользователь нажимает «Сохранить покупку» (либо в меню «Ещё» выбирает «Сохранить как шаблон»).
  6. `EditorModel.worker` атомарно сохраняет покупку в `receiptbox.db` (`ReceiptStore.save()`) и очищает `DraftCache`.
  7. Прецедент завершается.
- **Альтернативные потоки:**
  - **A1 (Чек без позиций):** пользователь указывает только положительную итоговую сумму (`totalMinor > 0`, `items = []`); система допускает сохранение одной операцией без создания фиктивных строк.
  - **A2 (Поворот экрана или сворачивание приложения):** промежуточное состояние формы сохраняется в `EditorModel` / `DraftCache` без записи в основную БД.
  - **A3 (Сохранение как шаблон, F-16):** пользователь в меню редактора «Ещё» выбирает «Сохранить как шаблон», вводит название (1–80 симв.) и подтверждает; `ReceiptStore.saveTemplate()` записывает заготовку в таблицу `receipt_templates`.
- **Потоки ошибок:**
  - **E1 (Нарушение доменной валидации):** дата вне диапазона `2000-01-01..today + 1 год`, более `200` позиций, пустое название или некорректная сумма — сохранение отклоняется с выводом текста ошибки пользователю.
- **Постусловия:** Покупка (или шаблон в `receipt_templates`) сохранена в `receiptbox.db`, `DraftCache` очищен.

### UC-03: Найти покупки, просмотреть каталог товаров и историю цен

- **Краткое описание:** Позволяет пользователю фильтровать и сортировать сохранённые чеки, переключать режим отображения («карточки / список»), просматривать каталог товаров с динамикой цен за единицу и массово менять категорию товара.
- **Актёры и связи:** Владелец архива (инициатор).
- **Предусловия:** Приложение запущено; для отображения позиций в архиве имеется хотя бы одна сохранённая покупка (иначе выводится пустое состояние).
- **Основной поток событий:**
  1. Прецедент начинается, когда пользователь открывает вкладку «Покупки» (`ReceiptBrowser`) или «Товары» (`ProductBrowser`) в `MainActivity`.
  2. В разделе «Покупки» пользователь вводит поисковый запрос (магазин, товар или дату) и/или выбирает сортировку и режим карточек/списка.
  3. `ReceiptStore` выполняет индексированный локальный SQL-запрос (≤ `2,0 с` для `1000` чеков) и обновляет список на экране.
  4. Во вкладке «Товары» `ReceiptStore.products()` группирует позиции по `(product_key, currency)` и отображает последнюю, минимальную и максимальную цены за единицу.
  5. Пользователь выбирает конкретный товар и открывает диалог истории цен (`ReceiptStore.history()`), упорядоченный по дате покупки.
  6. Прецедент завершается.
- **Альтернативные потоки:**
  - **A1 (Массовое изменение категории товара):** пользователь в режиме выбора отмечает один или несколько товаров и назначает новую категорию; `ReceiptStore.setProductCategory()` обновляет все соответствующие строки таблицы `items` пакетами ≤ `400` ID в транзакции.
  - **A2 (Смена режима отображения и сортировки):** выбор пользователя сохраняется раздельно для покупок и товаров в `AppPreferences`.
- **Потоки ошибок:**
  - **E1 (Ничего не найдено):** при пустом результате фильтрации выводится сообщение об отсутствии совпадений без изменения данных БД.
- **Постусловия:** Пользователю показан актуальный список покупок или история цен товара; настройки отображения сохранены в `AppPreferences`.

### UC-04: Анализировать мультивалютные расходы и контролировать бюджет

- **Краткое описание:** Позволяет пользователю просматривать месячную сводку расходов по категориям и банковским картам в выбранной валюте отчёта с точным пересчётом по историческим курсам НБРБ и контролем лимита бюджета.
- **Актёры и связи:** Владелец архива (инициатор); включает `<<include>>` **UC-10 (Загрузить и кэшировать исторический курс НБРБ)**.
- **Предусловия:** Пользователь открыл вкладку «Расходы»; выбраны расчётный месяц (`MonthChooser`) и валюта отчёта (`AppPreferences.baseCurrency()`).
- **Основной поток событий:**
  1. Прецедент начинается, когда пользователь переходит на вкладку «Расходы» или меняет месяц/валюту отчёта.
  2. При наличии покупок в валюте, отличной от валюты отчёта, выполняется включённый прецедент **UC-10** для загрузки недостающих исторических котировок в локальный кэш `exchange_rates`.
  3. `ReceiptStore.statsConverted()` и `cardSpending()` считывают курсы из кэша `exchange_rates` и методом `HistoricalRate.convertMinor()` пересчитывают суммы категорий и чеков через `BYN` с учётом `scale`, деноминации 2016 г. и единственного округления `HALF_UP`.
  4. Разница между суммой сконвертированных категорий и итогом чека (скидки, округление) явно выносится в строку «Корректировка чека».
  5. Если для пары `(month, currency)` задан лимит в `monthly_budgets`, `BudgetProgress.of()` рассчитывает процент освоения и статус (`NORMAL` < 80%, `NEAR_LIMIT` 80–100%, `OVER_LIMIT` > 100%).
  6. Интерфейс отображает общую сумму, индикатор бюджета, разбивку по категориям и по картам (включая «Без карты»).
  7. Прецедент завершается.
- **Альтернативные потоки:**
  - **A1 (Настройка месячного бюджета):** пользователь в разделе «Настройки» задаёт сумму лимита для `(month, currency)` (`0` — без ограничения); `SettingsPanel` сохраняет лимит в `monthly_budgets`, индикатор на вкладке «Расходы» пересчитывается.
  - **A2 (Отсутствует один или несколько курсов НБРБ):** `missingRateCount > 0`; система отображает сумму только по конвертированным чекам, помечает сводку звёздочкой (`*`) как неполную и откладывает стартовое предупреждение о бюджете до загрузки недостающих котировок.
- **Потоки ошибок:**
  - **E1 (Ошибка чтения БД):** отображается неблокирующее уведомление без потери сохранённых данных.
- **Постусловия:** Отображена достоверная мультивалютная сводка расходов и статус выполнения месячного бюджета.

### UC-05: Выполнить массовое удаление и выборочный TXT-экспорт

- **Краткое описание:** Позволяет пользователю в режиме множественного выбора привязать карту к группе чеков, безопасно удалить выбранные покупки либо сформировать выборочный UTF-8 TXT-файл для отправки через системное меню «Поделиться».
- **Актёры и связи:** Владелец архива (инициатор), Системные службы Android (`FileProvider`), Планировщик времени ОС (TTL-очистка кэша старше 24 часов).
- **Предусловия:** В архиве покупок или каталоге товаров есть хотя бы одна запись; активирован режим множественного выбора (`SelectionModel`).
- **Основной поток событий:**
  1. Прецедент начинается, когда пользователь длительным нажатием активирует множественный выбор и отмечает нужные покупки или товары.
  2. Пользователь нажимает кнопку «Поделиться» в нижней панели действий (`SelectionActionsView`).
  3. `SelectionSharing` удаляет в каталоге `cache/shares/` устаревшие временные файлы старше 24 часов (по системному времени) и записывает UTF-8 TXT только из выбранных покупок/товаров (без `rawText`, фото и реквизитов карт).
  4. Системные службы Android через `FileProvider` с флагом `FLAG_GRANT_READ_URI_PERMISSION` открывают системный диалог выбора внешнего приложения для отправки файла.
  5. Прецедент завершается.
- **Альтернативные потоки:**
  - **A1 (Массовое удаление чеков):** пользователь нажимает «Удалить» и подтверждает действие; `ReceiptStore.deleteReceipts()` удаляет записи пакетами ≤ `400` ID в ACID-транзакции и удаляет JPEG-файлы с диска только при обнулении ссылок в `receipts`, `pending` и `DraftCache`.
  - **A2 (Массовая привязка карты):** пользователь нажимает «Карта» и выбирает карту (или «Без карты»); `ReceiptStore.setReceiptCards()` обновляет `card_id` пакетами ≤ `400` ID.
  - **A3 (Изменение фильтра или поворот экрана):** `SelectionModel` сохраняет выделение и синхронизирует его с видимым списком.
- **Потоки ошибок:**
  - **E1 (Ошибка записи TXT-файла):** неполный временный файл удаляется в блоке `finally`, а выделение сохраняется для повторной попытки.
- **Постусловия:** Выбранные данные переданы во внешнее приложение через `FileProvider` либо чеки/карты атомарно обновлены в `receiptbox.db`.

### UC-06: Управлять справочником банковских карт

- **Краткое описание:** Позволяет пользователю просматривать, добавлять, редактировать и удалять локальные записи банковских карт (название и последние 4 цифры) для привязки к покупкам и анализа расходов по картам.
- **Актёры и связи:** Владелец архива (инициатор).
- **Предусловия:** Открыт раздел «Настройки» (`SettingsPanel`) или диалог выбора карты в редакторе (`CardManager`).
- **Основной поток событий:**
  1. Прецедент начинается, когда пользователь нажимает «Банковские карты» в настройках (или выбирает «Добавить карту» в выборе карты).
  2. `CardManager` загружает список карт из `ReceiptStore.cards()` и отображает диалог управления.
  3. Пользователь выбирает «Добавить карту» или конкретную карту → «Изменить».
  4. Пользователь вводит название карты (`label`, 1–80 симв.) и последние 4 цифры (`last_four`, ровно 4 ASCII-цифры) и нажимает «Сохранить».
  5. `ReceiptStore` валидирует поля и сохраняет запись в таблице `bank_cards`.
  6. Прецедент завершается; список карт обновляется и доступен для автоподбора по `last_four` и привязки к чекам.
- **Альтернативные потоки:**
  - **A1 (Удаление карты):** пользователь выбирает карту → «Удалить» и подтверждает действие; `ReceiptStore.deleteCard()` удаляет запись из `bank_cards`, а SQLite по внешнему ключу `ON DELETE SET NULL` автоматически снимает привязку `card_id` у покупок и шаблонов без удаления самих чеков.
- **Потоки ошибок:**
  - **E1 (Некорректные реквизиты):** ввод не 4 цифр (включая полный PAN) блокируется фильтром ввода на UI, проверкой `cardValues()` в Java и ограничением `CHECK(length(last_four)=4)` в SQLite.
- **Постусловия:** Справочник `bank_cards` обновлён без хранения полного номера карты, срока действия и CVV.

### UC-07: Создать и восстановить локальную резервную копию архива (SAF, F-15)

- **Краткое описание:** Позволяет пользователю явно экспортировать полный версионируемый JSON/ZIP-архив всех данных Cheq через системный Android Storage Access Framework и атомарно восстановить его без дублей на текущем или новом устройстве.
- **Актёры и связи:** Владелец архива (инициатор), Системные службы Android (`Storage Access Framework`).
- **Предусловия:** Открыт раздел «Настройки» (`SettingsPanel`).
- **Основной поток событий:**
  1. Прецедент начинается, когда пользователь в разделе «Настройки» → «Резервная копия» нажимает «Экспорт архива (ZIP)».
  2. Системные службы Android открывают системный диалог `ACTION_CREATE_DOCUMENT` (SAF); пользователь выбирает папку и имя файла (`cheq-backup-YYYY-MM-DD.zip`).
  3. `SettingsPanel.exportBackup()` на фоновом потоке вызывает `ReceiptStore.exportSnapshot()`, считывая карты, чеки, позиции, бюджеты, кэш курсов и шаблоны в консистентной транзакции чтения.
  4. `BackupCodec.encodeZip()` (`:core`) валидирует снимок (`schemaVersion = 6`) и записывает UTF-8 JSON (`cheq-backup.json`) в ZIP-поток по полученному `content://` URI.
  5. Пользователю выводится подтверждение с количеством сохранённых чеков; прецедент завершается.
- **Альтернативные потоки:**
  - **A1 (Атомарное восстановление из резервной копии):**
    1. Пользователь нажимает «Восстановить из файла»; Android SAF открывает диалог `ACTION_OPEN_DOCUMENT`.
    2. `SettingsPanel.importBackup()` передаёт поток `BackupCodec.decodeZip()`, который проверяет размер (≤ `10 МБ`), формат ZIP/JSON, `schemaVersion` (`1..6`) и все доменные ограничения **до** открытия транзакции БД.
    3. `ReceiptStore.restoreAtomic()` в единой ACID-транзакции сопоставляет карты, пропускает уже существующие чеки и шаблоны (защита от дублей), добавляет новые записи и обновляет бюджеты/курсы.
    4. Интерфейс обновляет статистику и уведомляет о количестве восстановленных чеков и шаблонов.
- **Потоки ошибок:**
  - **E1 (Повреждённый файл, превышен лимит 10 МБ или неподдерживаемая `schemaVersion > 6`):** `BackupCodec` выбрасывает `IllegalArgumentException` до открытия транзакции `receiptbox.db`; текущие данные пользователя остаются нетронутыми.
- **Постусловия:** Валидный ZIP-архив сохранён по выбранному SAF URI либо данные архива атомарно восстановлены в `receiptbox.db` v6 без дублей.

### UC-08: Проверить арифметику и валидность чека (`<<include>>`)

- **Краткое описание:** Включаемый прецедент, выполняющий доменную валидацию полей черновика (`ReceiptDraft.validate()`) и независимую проверку арифметической согласованности строк и итога (`ReceiptArithmetic.discrepancies()`) перед сохранением покупки.
- **Актёры и связи:** Включается (`<<include>>`) прецедентами **UC-01** и **UC-02**; самостоятельным актёром напрямую не вызывается.
- **Предусловия:** В редакторе или после облачного разбора сформирован черновик `ReceiptDraft`.
- **Основной поток событий:**
  1. Система проверяет доменные ограничения в `ReceiptDraft.validate()`: магазин (1–160 симв.), дата (`2000-01-01..today + 1 год`), поддерживаемая валюта (`BYN`, `RUB`, `EUR`, `USD`, `KZT`, `PLN`), число позиций (≤ `200`), ненулевой итог при пустом списке позиций и корректность каждой строки.
  2. `ReceiptArithmetic.discrepancies()` для каждой позиции сверяет `|round_HALF_UP(unitMinor × quantityMilli / 1000) − lineMinor| ≤ 1`.
  3. При непустом списке позиций проверяет итоговую сумму чека: `|sum(lineMinor) − totalMinor| ≤ 1`.
  4. При отсутствии нарушений проверка подтверждает готовность к сохранению; прецедент завершается.
- **Альтернативные потоки:**
  - **A1 (Выявлено расхождение сумм > 0,01):** система формирует наглядное предупреждение «Суммы отличаются» (позиции vs итог по чеку) и запрашивает явное подтверждение пользователя «Сохранить» или возврат к правкам («Проверить») без скрытой автоподгонки сумм.
- **Потоки ошибок:**
  - **E1 (Нарушены жёсткие инварианты `ReceiptDraft.validate()`):** сохранение блокируется с отображением сообщения о конкретном некорректном поле.
- **Постусловия:** Валидность черновика проверена; при расхождении пользователь уведомлён и принял осознанное решение о сохранении.

### UC-09: Обработать офлайн-очередь и повторы (`<<extend>>`)

- **Краткое описание:** Расширяющий прецедент, обеспечивающий гарантированное фоновое доведение отложенных или завершившихся сбоем импортов из `pending_receipts.db` до состояния `ready` при восстановлении сети, истечении backoff-таймера или перезапуске приложения.
- **Актёры и связи:** Расширяет (`<<extend>>`) прецедент **UC-01** (точка расширения: ожидание сети / ошибка разбора); взаимодействует с **Планировщиком времени ОС**, **Системными службами Android** (`ConnectivityManager`) и **Groq API**.
- **Предусловия:** В таблице `pending` базы `pending_receipts.db` имеется хотя бы одна запись со статусом `waiting`, `error` или прерванным при крахе `processing`.
- **Основной поток событий:**
  1. Прецедент активируется по событию перезапуска приложения (`PendingReceiptStore.recover()`), восстановлению валидированной сети (`NetworkCallback.onCapabilitiesChanged` с `NET_CAPABILITY_VALIDATED`) или срабатыванию таймера `ScheduledExecutorService` после истечения `retry_after`.
  2. `RecognitionQueue.schedule()` рассчитывает ближайшую задержку для неготовых записей (дедупликация попыток в рамках цикла по ключу `id:revision`) и запускает `drain()`.
  3. Для каждой подходящей записи с непустым `raw_text` при наличии сети и `now ≥ retry_after` очередь переводит статус в `processing` и повторно отправляет запрос в Groq API (`GroqClient.parse()`).
  4. При получении валидного ответа и совпадении `CAS revision` запись переводится в `ready`, а UI обновляется через слушателей `RecognitionQueue`.
  5. Прецедент завершается.
- **Альтернативные потоки:**
  - **A1 (Сбой процесса во время предыдущего разбора):** при инициализации `RecognitionQueue` метод `PendingReceiptStore.recover()` сбрасывает все записи из `processing` обратно в `waiting` без потери фото и текста.
  - **A2 (Покупка уже была сохранена до сбоя удаления из очереди):** `RecognitionQueue` сверяется с таблицей `completed_pending` и удаляет отработанную запись из `pending_receipts.db`.
- **Потоки ошибок:**
  - **E1 (Повторная ошибка сети/API):** счётчик `failures` увеличивается (`min(failures + 1, 6)`), вычисляется `retry_after = now + min(60 000, 2 000 << (failures − 1))`, запись переводится в `error` (или `waiting` при отсутствии сети) без бесконечного цикла самоповторов.
- **Постусловия:** Записи очереди либо доведены до `ready` / очищены по `completed_pending`, либо перенесены на следующий контролируемый интервал повтора.

### UC-10: Загрузить и кэшировать исторический курс НБРБ (`<<include>>`)

- **Краткое описание:** Включаемый прецедент, запрашивающий у публичного API НБРБ официальные исторические курсы валют на конкретные даты покупок и сохраняющий их в локальный кэш `exchange_rates`.
- **Актёры и связи:** Включается (`<<include>>`) прецедентом **UC-04**; взаимодействует с внешней системой **API НБРБ**.
- **Предусловия:** В архиве присутствуют покупки в валюте, отличной от выбранной валюты отчёта, либо отсутствуют котировки `(currency, purchase_date)` в таблице `exchange_rates` на даты ≤ сегодняшней.
- **Основной поток событий:**
  1. `ReceiptStore.missingRateRequests(baseCurrency)` определяет уникальный перечень недостающих пар `(currency, purchase_date)` (включая валюту отчёта, если она не `BYN`).
  2. `HistoricalRateRepository.refreshMissingRates()` группирует запросы по уникальным датам, пропуская будущие даты и пары в периоде 60-секундного backoff.
  3. Для каждой даты `NbrbRateClient` (пул `nbrb-http`, таймаут `12 с`) выполняет HTTPS GET `https://api.nbrb.by/exrates/rates?ondate=YYYY-MM-DD&periodicity=0`.
  4. При HTTP 200 система парсит поля `Cur_Abbreviation`, `Cur_Scale`, `Cur_OfficialRate` и сверяет дату котировки `Date` с запрошенной датой.
  5. `ReceiptStore.saveRate()` сохраняет полученные котировки в таблицу `exchange_rates`.
  6. При наличии обновлённых курсов `MainActivity` обновляет экран расходов и проверку бюджета.
  7. Прецедент завершается.
- **Альтернативные потоки:**
  - **A1 (Валюта отсутствует в общей сводке НБРБ на дату, например исторический или редкий период):** система выполняет точечный запрос `GET /exrates/rates/{ISO}?parammode=2&ondate=YYYY-MM-DD`.
  - **A2 (Все требуемые котировки уже есть в кэше):** сетевые запросы не выполняются (`0` обращений к API НБРБ).
- **Потоки ошибок:**
  - **E1 (Нет интернета, таймаут 12 с или несовпадение даты в ответе):** запрос прерывается (`Future.cancel(true)`), на пару `(currency, date)` выставляется 60-секундный backoff (сбрасывается при восстановлении сети по `NetworkCallback`), а исходные покупки остаются в неизменной валюте.
- **Постусловия:** Загруженные котировки закэшированы в `exchange_rates` для автономного пересчёта; при сетевом отказе выставлен backoff без блокировки UI.
